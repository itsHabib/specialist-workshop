# Real test-history trial for the Decision Model Maker

**Decision to earn.** Can a fresh adopter use the maker to get an actionable test failure back sooner on a real change, at an acceptable cost on the rest of the workload? The host still runs its required checks to completion. The user-visible result is the time to trustworthy feedback. Choosing to retain the existing order or a small coded improvement is a successful trial outcome.

The maker can now package a trained tree with the host's decision settings. We trained a Click tree on historical jobs to test that handoff. The available later Click history has one uninspected failing test command in the chosen environment. That limits the evidence for improving feedback on new defects. A separate comparison on Paint Control found the simple five-cycle rule competitive with the tree. ## Does a code dependency identify a better first test?

We tested a coded ordering rule using only the collected test IDs, tested source and changed paths. It keeps changed test files first, promotes test functions that directly reference a changed source module, then functions referencing a module that imports the changed one. Remaining tests and ties retain native order. The rule recognizes explicit imports and a single package re-export. It reads the syntax trees without importing the application. ## Establish the comparison before opening the holdout

1. **Unit and scope.** Start with one serial Ubuntu/Python environment. A build, matrix row, failed test and independent software change are different units. Group related PR revisions, retries and manifestations of the same defect. Keep green changes for overhead and prevalence. Keep setup failures, incomplete runs, cancellations, expected failures and uncertain flakes visible with separate reasons. A partially executed suite stays incomplete. Reconcile expected nodes against an independently collected roster.
2. **Time of knowledge.** At dispatch allow the tested diff, candidate IDs available from collection, and prior completed runs visible at that time. A failure from a concurrent job is available only after its result arrived. Outcomes, durations and coverage measured on the change belong to the grader, unless the policy explicitly buys and pays for an observation before its deadline. Change future outcomes and verify that earlier choices and features remain identical.
3. **Can a reordered log be trusted?** Use recorded full-suite results for counterfactual prefixes only after running both prefixes from equivalent clean states on a sample of green, failing and discordant changes. Compare failure identities, order-dependent behavior and elapsed time. Fresh and warm caches, fixture sharing, fail-fast skips and parallel workers can change these results. If verdicts transfer but clocks do not, report tests consumed to first failure. If verdicts change, use paired actual executions or mark the case unscorable.
4. **Freeze the rules.** Split by chronological change families, with related revisions on one side and only matured outcomes entering training. Keep inspected witnesses in development. Hash the holdout list of change families, actual tested SHAs, environments and exclusions before running competing orders. Apply the same independent matched-environment rerun rule to establish a reference failing set on each change. A policy that masks a confirmed failure incurs a miss. An order-induced spurious failure counts as harm. Keep genuinely unknown pairs in the accounting. Choose the strongest coded control on development changes and freeze one tree, feature list and tie order. A history-free test falls back to the host's documented order. Give all policies access to the same evidence. Test neutral tie ordering against the learned tie rule so gains from a hidden heuristic stay visible.
5. **Measure the user's wait.** Proposed primary measure is paired time to the first reproducible actionable failure, capped at a common budget B, on confirmed failing changes. A policy that misses within B incurs B. Count misses and cases that could not be graded separately. Include collection, features, ranking, dispatch and verifier startup from the same clock origin. Use the host's feedback deadline if known. The study default is one quarter of the median full-suite development time, frozen before holdout. Also report per-arrival impact across green and red changes, green-run overhead, and detection at one and five attempts as diagnostics. Normal completion of the full suite remains the gate for a green build.
6. **Decide what would earn the model.** Proposed research target is at least a 10% reduction relative to the strongest rule's development mean capped wait on failing changes, expressed in seconds before opening the holdout. An adopter may replace this with its own meaningful target beforehand. Require a paired uncertainty interval over independent change families, counts of gains and losses, and the effect of missing pairs on the conclusion. A lower interval bound above the meaningful target, with acceptable missed-failure rate and overhead under prespecified host limits, earns a shadow trial. A wide interval earns more observation. When even a favorable hindsight order gains too little, keep the coded rule. Fifty failing commits is a planning estimate. Independent defects, discriminating cases and the uncertainty on the paired effect determine what the report can say.

The winner ranks by the mean failure fraction across each test's five most recently observed cycles. Equal scores use numeric test ID. Historical features use only completed earlier cycles. Repeated observations of a name in an earlier cycle contribute that cycle’s mean failure fraction once. The recorded duration is approximate. The comparison assumes that a recorded verdict transfers under reordering.

**Where to spend depth next.** Keep the first losing change small enough to replay. If the incident had no meaningful choice, improve coverage or the executor. If the tree loses because tests are indistinguishable, let a controller buy one extra pre-run observation and charge its complete cost. If a better first choice delays subsequent jobs, compare one budget allocator with a simple priority queue under contention. Advance to multiple learned stages only after a single stage has verified value and there is evidence of a second, distinct decision. Application-specific traces and learned policies stay with the adopting application.

**Handback at each checkpoint.** Record the source and model revisions, commands, arrivals and exclusions, earliest uncertainty, and either one independently verified behavior change or its precise blocker. Keep raw logs and checkpoints local. The final review should be able to distinguish reproducible correctness, better operational outcomes and a successful cold adoption.
